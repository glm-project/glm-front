# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`glmfront` is an Angular 21 single-page application, generated by [Seed4J](https://github.com/seed4j/seed4j), that authenticates users against **Keycloak** (OIDC, via `keycloak-js`). The codebase enforces a **hexagonal architecture with DDD bounded contexts**, checked automatically at test time by `arch-unit-ts`. Read `documentation/hexagonal-architecture.md` before adding new business code — it explains the _why_, this file focuses on the _how_ for this specific repo.

## Commands

```bash
npm run dev              # serve app + watch (http://localhost:9000)
npm run build             # production build (target/classes/static)

npm test                  # alias for watch:test (ng test --watch, Vitest via Angular's unit-test builder)
ng test --watch=false      # run the unit suite once
ng test --watch=false -- <pattern>   # run a subset (Vitest CLI args after `--`), e.g. -- oauth2-auth
npm run test:coverage      # unit tests with Istanbul coverage report (target/test-results)

npm run test:component     # Cypress component tests (boots the dev server first)
npm run test:component:headless
npm run e2e                 # Cypress e2e tests, interactive (expects app already running on :9000)
npm run e2e:headless

npm run lint                # eslint .
npm run prettier:check
npm run prettier:format
npx tsc --noEmit           # type-check without emitting
```

**Always run unit tests through `ng test`, never bare `npx vitest run`.** Angular 21's `@angular/build:unit-test` builder (configured in `angular.json`) injects the zoneless TestBed environment and JIT compiler setup that Angular component specs need; invoking Vitest directly skips that wiring and specs will fail with unrelated-looking errors (`TestBed.initTestEnvironment()`, JIT compiler not available).

Coverage is enforced **per file at 100%** (see `vitest.config.ts` `coverage.thresholds`) — a new file with untested branches fails the suite, not just lowers a global number. Write the test alongside the code, not after.

## Architecture: hexagonal + bounded contexts

Business code lives under `src/main/webapp/app/`. Each **bounded context** is a top-level folder there (currently `home`, `shared`) containing:

```
<context>/
  package-info.ts     # marks the context root — required for it to be picked up
  domain/              # business logic, framework-agnostic, no outside deps
  application/          # orchestration only: call ports, no business rules
  infrastructure/
    primary/            # adapters that drive the context (e.g. Angular components/routes)
    secondary/          # adapters implementing domain ports (HTTP clients, etc.)
```

`package-info.ts` must extend either `BusinessContext` (`@/app/BusinessContext`) or `SharedKernel` (`@/app/SharedKernel`) — this is how `arch-unit-ts` discovers contexts, not folder naming alone. Code that is genuinely shared across contexts belongs in a context extending `SharedKernel` (e.g. `shared`), not scattered into each context.

These rules are enforced by `src/test/webapp/unit/HexagonalArchTest.spec.ts` (runs as a normal Vitest unit test, so it fails the build like any other test):

- A context's code may not import another context's `domain`. Cross-context calls go through a primary adapter.
- Primary adapters meant to be called from another context must be named with a `TypeScript` prefix and may only be depended on from a `secondary` package (never called directly by UI code).
- `domain` may only depend on `domain` and shared kernels — nothing else, no Angular imports.
- `application` may not depend on `infrastructure`.
- `primary` may not depend on `secondary`, and vice versa (they only communicate through `application`/`domain`).
- Within a layered `application service` context, layers ordering is `domain models/services → application → primary/secondary adapters`; `primary`/`secondary` may not be depended on by anything.

When adding a bounded context, add its `package-info.ts` first — otherwise `arch-unit-ts` silently won't check it.

The `@/*` path alias resolves to `src/main/webapp/*` (configured in `tsconfig.json`, consumed via `vite-tsconfig-paths` in `vitest.config.ts`); prefer it over long relative paths (`../../../..`) when crossing context boundaries through a primary adapter.

## Authentication (Keycloak)

- `Oauth2AuthService` (`src/main/webapp/app/auth/oauth2-auth.service.ts`) wraps `keycloak-js`: exposes `token`, `isAuthenticated`, `initAuthentication()` (redirect-based login, `onLoad: 'login-required'`) and `logout()`, and silently refreshes the token (`MIN_TOKEN_VALIDITY_SECONDS = 70`).
- `httpAuthInterceptor` (`src/main/webapp/app/auth/http-auth.interceptor.ts`) attaches `Authorization: Bearer <token>` to every outgoing HTTP request; it's wired in `main.ts` via `provideHttpClient(withInterceptors([httpAuthInterceptor]))`.
- The Keycloak client itself is provided as a DI token in `main.ts` (`{ provide: Keycloak, useFactory: ... }`), configured from `environments/environment*.ts` (`keycloak.url` / `realm` / `client_id`). Don't hardcode Keycloak config elsewhere — read it from `environment`.
- Any new HTTP-calling secondary adapter gets auth for free through the interceptor; don't re-implement token attachment locally.
- Test doubles: mock `Oauth2AuthService` in unit/component specs (see `app.spec.ts`) rather than hitting a real Keycloak instance.

## Testing strategy (TDD)

Three layers, each with a distinct purpose — write the test first at the layer that matches what you're changing:

1. **Unit tests (Vitest)** — co-located `*.spec.ts` next to the source file (e.g. `oauth2-auth.service.spec.ts` beside `oauth2-auth.service.ts`), plus architecture tests in `src/test/webapp/unit/`. Use these for domain logic, services, interceptors, pipes — anything testable without a real DOM/router integration. 100% per-file coverage is enforced.
2. **Component tests (Cypress)** — `src/test/webapp/component/<context>/*.spec.ts`, run against the real dev server (`npm run test:component`). Use these to verify a component renders and behaves correctly in a browser, with network calls intercepted (`src/test/webapp/component/utils/Interceptor.ts` has `interceptForever` for controlling response timing).
3. **E2E tests (Cypress)** — `src/test/webapp/e2e/<context>/*.spec.ts` (`npm run e2e`), black-box through the full app against a running server. Reserve for user-journey-level checks, not component detail.

Shared convention: select elements via `data-selector` (or `data-cy`/`data-test`/`data-testid`) attributes and the `dataSelector()` helper (`src/test/webapp/{component,e2e}/utils/DataSelector.ts`) — don't select on CSS classes or text content, which are styling/i18n concerns.

## Code style & conventions

- ESLint is strict: `main/webapp/**` uses `typescript-eslint` `strictTypeChecked` + `stylistic` + `angular-eslint` recommended (see `eslint.config.mjs`). Component/directive selectors must use the `seed` prefix (`seed-login`, not `app-login`).
- Angular components are standalone by default (no `NgModule`), use `signal()` for local state (see `App.appName`) and `inject()` over constructor injection.
- Prettier: single quotes, no semicolon surprises, 140-char print width, `arrowParens: avoid`. Run `npm run prettier:format` — don't hand-format.
- Husky + lint-staged run `eslint --fix` and `prettier --write` on staged files before commit; don't bypass with `--no-verify`.
- `# seed4j-needle-*` comments (in `app.route.ts`, `main.ts`, `README.md`) are insertion points used by Seed4J module generators — keep them when editing those files by hand.

## SOLID / design guidelines for this codebase

- **SRP**: a `domain` class does one business thing; HTTP/serialization concerns belong in `infrastructure/secondary`, not mixed into domain models.
- **OCP/LSP**: define ports (interfaces) in `domain`, implement them in `infrastructure/secondary` — new integrations mean a new adapter, not edits to domain logic.
- **ISP**: keep ports narrow and specific to what the domain actually calls, not a catch-all repository/service interface.
- **DIP**: `domain`/`application` depend on abstractions (ports) they own; `infrastructure` depends inward on those abstractions, never the reverse — this is exactly what the `arch-unit-ts` layered-architecture check enforces, so a failing architecture test usually signals a DIP violation.
